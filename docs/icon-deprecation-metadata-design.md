# Icon deprecation metadata design

## Summary

> The shared deprecation contract this design builds on was reduced to `Deprecation`, `Deprecated<T>`, `Deprecations`,
> `isDeprecated` and `getDeprecationComment` — see
> [`docs/deprecation-contract-design.md`](./deprecation-contract-design.md), which is authoritative wherever the prose
> below names a removed helper.

Icon deprecations shall be owned by `@porsche-design-system/icons`, which already generates `ICONS_MANIFEST`,
`ICON_NAMES`, and `IconName` from SVG assets. The package shall additionally export current icon metadata and an
explicit `iconDeprecationsMeta`, initially empty.

The knowledge skill imports icon deprecations directly. `componentMeta['p-icon'].propsMeta.name` remains compatible but
derives deprecated icon values from the icon-owned metadata rather than becoming the source.

This design follows the conventions established by the implemented
[SCSS deprecation metadata design](./scss-deprecation-metadata-design.md#conventions-for-other-sources). The
literal-object authoring convention applies to the deprecation descriptors that feed the build, not to the generated
metadata itself.

## Architecture & approach

```text
SVG assets + icon deprecation descriptors
  -> icons build
  -> iconMeta + iconDeprecationsMeta
  -> ICONS_MANIFEST / ICON_NAMES compatibility surface
  -> p-icon allowed/deprecated values
  -> knowledge-skill deprecations.md
```

Icon ownership moves from an incidental component prop-value interpretation to the package that owns icon names and
files.

## Components

### Icon metadata

Add a small generated node plus a deprecated subtype that requires the lifecycle detail:

```ts
export type IconDeprecation = {
  /** Optional note replacing the package default lifecycle sentence. */
  message?: string;
  replacement?: IconName;
};

export type IconMeta = {
  name: IconName;
};

export type DeprecatedIconMeta = IconMeta & {
  deprecation: IconDeprecation;
};
```

`IconMeta` carries no `deprecation`, so a deprecated icon cannot be emitted into `iconMeta` and a current one cannot be
emitted into `iconDeprecationsMeta` without a compile error.

`iconMeta` contains recommended icon names. `iconDeprecationsMeta` contains deprecated names in authored descriptor
order. Both are generated by `packages/assets/projects/icons/scripts/build.ts`.

Icon names need no decoration, so identity is the name itself; `replacement` is typed as `IconName` rather than a free
string, which gives the same rename safety the identity helper gives elsewhere.

Default wording is fixed and shared with the other sources:

- with replacement: `This API will be removed with the next major release.`;
- without replacement: `This API will be removed with the next major release and has no replacement.`.

Expose `iconDeprecationMessage(node)` for the lifecycle sentence the knowledge skill records as `message`; the skill
renders `replacement` in its own column and implements no fallback wording.

### Compatibility exports

`ICON_NAMES` and `IconName` currently form a public compatibility surface. They continue to include every supported
icon, including deprecated names, until removal. A current-only list may be exported for documentation, but existing
exports must not silently drop deprecated names.

For a renamed icon, the build may keep a legacy SVG or generate a manifest alias to the replacement. The descriptor is
authoritative for replacement and message.

### Component-meta integration

`p-icon` continues validating all supported `ICON_NAMES`. Other component props such as `icon` and `actionIcon` also
continue accepting supported names. Component-meta generation obtains:

- allowed values from all supported names;
- deprecated values from `iconDeprecationsMeta`;
- per-value deprecation details from the same source.

The component deprecation catalog excludes these values so the knowledge index reports each deprecated icon name only
once in the Icons category. The existing `value/p-icon/name/<name>` identity remains the canonical audit rule for the
shared icon vocabulary; its bare-value spelling allows the audit to validate uses in other icon-valued component props
without creating one rule per owner.

### Knowledge-skill adapter

Replace `collectIconDeprecations()` in `collectors/scanned.ts` with a direct import from `@porsche-design-system/icons`.
The adapter adds `value/p-icon/name/<name>` IDs, component context, and `references/icons.md`, sets `message` from
`iconDeprecationMessage(node)` and carries `replacement` through. It preserves metadata order and performs no filesystem
access.

## Data & state

The stable identity is the kebab-case icon name. The icons package owns lifecycle, replacement, manifest mapping, and
order. The component package owns only the `p-icon` API projection. The skill owns audit IDs and reference links.

## Trade-offs

Keeping icon ownership in component metadata is simpler today but creates duplicate reporting when icon values are also
treated as component values. Package ownership allows other icon consumers to receive the same lifecycle information.

Adding `iconMeta` is more structure than an empty manifest alone, but it establishes a complete source for current icon
documentation and future deprecation partitioning.

## Risks & mitigations

| Risk                                                    | Mitigation                                                                                              |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| A deprecated icon disappears from `IconName` too early. | Build the compatibility union from current and deprecated metadata.                                     |
| Component and icon categories duplicate rule IDs.       | Assign icon-name entries exclusively to the Icons category.                                             |
| Manifest aliases point to missing files.                | Validate every current and deprecated name against a generated file or replacement target.              |
| Icon and component builds form a cycle.                 | Keep icon metadata generated in the existing low-level assets build and consume it from component-meta. |

## Testing strategy

Icons tests shall prove:

1. Current and deprecated icon names are unique and disjoint.
2. Their union equals the supported `ICON_NAMES` set.
3. Every manifest entry resolves to a generated asset.
4. Every replacement references a current icon.
5. The current release exports an explicit empty `iconDeprecationsMeta`.
6. A fixture entry receives the shared default wording for both the replacement and no-replacement cases.

Component-meta tests verify `p-icon` allowed and deprecated values derive from icon exports. Skills tests derive their
expectations from `iconDeprecationsMeta` using the package's own helper — never a hand-authored name list and never a
component-source read — and verify the empty category plus a deprecated fixture.

## Rollout

1. Add icon metadata types, the `DeprecatedIconMeta` subtype, the deprecation descriptor and the message helper.
2. Extend the icons build to emit current and deprecated metadata.
3. Preserve `ICON_NAMES`, `IconName`, and manifest compatibility.
4. Consume icon metadata in component-meta generation.
5. Replace the skill collector with the direct icon metadata adapter.
6. Remove icon deprecation derivation from generic component value collection.
7. Update assets, component-meta, icon-reference, and skill tests.

## Open questions

Whether the current-only name list is public or remains internal can be decided when icon documentation adopts it.
`ICON_NAMES` itself must retain its existing all-supported semantics.
