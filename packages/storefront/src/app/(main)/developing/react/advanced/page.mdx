## Global Theme

All system colors are controlled via the CSS
[`color-scheme`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme) property and are
included in our mandatory [Global Styles](/stylesheets/introduction). These styles also provide utility classes for
selecting the active theme and a polyfill to ensure compatibility with browsers that do not yet support `light-dark()`
(see [browser support](https://caniuse.com/mdn-css_types_color_light-dark)).

By default, color tokens use the light theme. To enable the dark theme or automatic theme switching based on system
settings, add the `.scheme-light`, `.scheme-dark` or `.scheme-light-dark` CSS class to the `<html>` element or any HTML
element. This applies the selected theme to all child elements.

Learn more in the [Theme](/must-know/theme) section.

## Typed Events and Element Refs

React components with custom events export concrete event and host element types, for example `PInputNumberInputEvent`,
`PInputNumberChangeEvent`, `PInputNumberBlurEvent`, and `PInputNumberElement`. Import these from
`@porsche-design-system/components-react`, or from `@porsche-design-system/components-react/ssr` in Next.js and React
Router SSR applications. Both entry points provide the same typings.

### Named and inline handlers

Replace a plain `CustomEvent<...EventDetail>` annotation with the concrete event type to access the host's properties
without a cast:

```diff
- import type { InputNumberInputEventDetail } from '@porsche-design-system/components-react';
+ import type { PInputNumberInputEvent } from '@porsche-design-system/components-react';

- function handleInput(event: CustomEvent<InputNumberInputEventDetail>) {
-   setValue((event.target as HTMLElement & { value: PInputNumberProps['value'] }).value);
+ function handleInput(event: PInputNumberInputEvent) {
+   setValue(event.target.value);
  }
```

Named functions need an annotation: TypeScript does not infer their parameter types backwards from a later
`onInput={handleInput}` assignment. Inline JSX handlers are inferred automatically:

```tsx
import { useState } from 'react';
import { PInputNumber, type PInputNumberProps } from '@porsche-design-system/components-react';

export function Quantity() {
  const [value, setValue] = useState<PInputNumberProps['value']>('');

  return (
    <PInputNumber
      name="quantity"
      label="Quantity"
      value={value}
      onInput={(event) => {
        setValue(event.target.value);
      }}
    />
  );
}
```

The inferred event is `PInputNumberInputEvent` and its `target` is `PInputNumberElement`, the `<p-input-number>` host.
Property unions and optionality are unchanged: `PInputNumberProps['value']` is still
`string | number | null | undefined`, not just `number`.

Existing `CustomEvent<InputNumberInputEventDetail>` handlers remain assignable, but that annotation loses the more
precise `target` type. `event.detail` remains the original payload; for this input event it is the native `InputEvent`.
`event.detail.target` is **not** newly typed as the PDS host. Other event detail payloads are unchanged too. Keep native
React event annotations, such as `FormEvent<HTMLFormElement>`, for native React events.

### Element refs and DOM listeners

Use the exported element type for object refs rather than intersecting `PInputNumberProps` with `HTMLElement`.
`PInputNumberProps` describes JSX props, including React attributes and callbacks, not the DOM element.

Ref typings are unchanged: callback refs infer `HTMLElement | null`, and React's `ComponentRef<typeof PInputNumber>`
remains `HTMLElement`. Existing object refs and forwarding components keep working. Automatic component-specific ref
inference and enforcement are deferred to V5.

Opt into accurate host properties and event types with `createRef<PInputNumberElement>()` or
`useRef<PInputNumberElement>(null)`. The ref points to `<p-input-number>`, not its inner `<input>`; accepting an
existing `HTMLInputElement` annotation does not make native input APIs available on the host.

```tsx
import { useEffect, useRef, useState } from 'react';
import {
  PInputNumber,
  type PInputNumberInputEvent,
  type PInputNumberElement,
  type PInputNumberProps,
} from '@porsche-design-system/components-react';

export function QuantityWithListener() {
  const inputRef = useRef<PInputNumberElement>(null);
  const [value, setValue] = useState<PInputNumberProps['value']>('');

  useEffect(() => {
    const element = inputRef.current;
    if (!element) return;

    const handleInput = (event: PInputNumberInputEvent) => {
      setValue(event.target.value);
    };
    element.addEventListener('input', handleInput);
    return () => element.removeEventListener('input', handleInput);
  }, []);

  return <PInputNumber ref={inputRef} name="quantity" label="Quantity" value={value} />;
}
```

Use either the DOM listener above or an `onInput` prop, not both for the same handler. `addEventListener` and
`removeEventListener` recognize the component's custom events while retaining native event and string-name fallbacks. An
inline listener passed to `element.addEventListener('input', (event) => { ... })` also infers the concrete event.

Alternatively, explicitly annotate a callback ref to use the exported host type. Inside a component using the `inputRef`
above, replace the object ref with:

```tsx
<PInputNumber
  name="quantity"
  label="Quantity"
  value={value}
  ref={(element: PInputNumberElement | null) => {
    inputRef.current = element;
  }}
/>
```

Element types are currently exported only for components with custom events. All components retain their existing ref
typings.

## Prefixing

In case of a micro-service architecture, multiple instances and versions of the Porsche Design System can be combined in
a final application. This could cause conflicts due to the way how custom webcomponents are registered in the browser.
During the bootstrap phase of the Porsche Design System, custom elements are defined. If a second application wants to
register Porsche Design System again it will cause issues especially when different versions are used.

A way of preventing those conflicts is by using a unique custom prefix for the components. Simply pass your desired
prefix to the `prefix` property of `PorscheDesignSystemProvider`.

```tsx
// index.tsx

import ReactDOM from 'react-dom';
import { PorscheDesignSystemProvider } from '@porsche-design-system/components-react';
import { App } from './App';

ReactDOM.render(
  <React.StrictMode>
    <PorscheDesignSystemProvider prefix="sample-prefix">
      <App />
    </PorscheDesignSystemProvider>
  </React.StrictMode>,
  document.getElementById('root')
);
```

In the following example the `PHeading` component will render as `<sample-prefix-p-heading>`.

```tsx
// App.tsx

import { PHeading } from '@porsche-design-system/components-react';

export const App = (): JSX.Element => <PHeading>Some heading</PHeading>;
```
