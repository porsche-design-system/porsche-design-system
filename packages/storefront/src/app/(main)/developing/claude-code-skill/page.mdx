# Claude Code Skill

<TableOfContents
  headings={['Installation', 'Choosing a Location', 'How It Works', 'Windows', 'Yarn PnP', 'Updating & Reinstalling']}
/>

Each Porsche Design System wrapper package ships a [Claude Code](https://docs.claude.com/en/docs/claude-code/overview)
skill named after the package — `porsche-design-system-components-js`, `…-angular`, `…-react` or `…-vue`. The skill
gives your AI assistant **version-exact** knowledge of the Porsche Design System components, styles and tokens that
match the exact package version you have installed, so it can answer questions, generate new code, and review or fix
existing usage.

The skill content lives inside the installed package in `node_modules`. To make it discoverable by Claude Code, a small
CLI creates a symlink from your project's `.claude/skills/` directory into the package.

## Installation

Run the bundled CLI once in your project root, using the wrapper package that matches your framework:

```bash
# Vanilla JS
npx --package=@porsche-design-system/components-js pds-skill

# Angular
npx --package=@porsche-design-system/components-angular pds-skill

# React
npx --package=@porsche-design-system/components-react pds-skill

# Vue
npx --package=@porsche-design-system/components-vue pds-skill
```

The `--package=…` form names both the package and the `pds-skill` binary explicitly. It is required for
`components-react` (which ships more than one binary, so a bare `npx @porsche-design-system/components-react pds-skill`
cannot determine which executable to run) and works uniformly for all four packages.

This creates the symlink `.claude/skills/porsche-design-system-components-<framework>` (e.g.
`.claude/skills/porsche-design-system-components-react`) pointing at the invoking package's `skill/` directory. The CLI
is **package-scoped**: it resolves its own package via the bin's own location, so the `react` CLI links the React skill
and never falls through to `@porsche-design-system/components-js` — even though `js` is always installed as a dependency
of the framework wrappers. Because the link is named after the package, installing more than one wrapper links each
skill side by side instead of colliding.

The command is **idempotent**: re-running it repoints or repairs the symlink it owns (including a dangling link from a
previously removed package). If the installed package version predates the skill (older releases ship no `skill/`
directory), the CLI is a **silent no-op**.

<Notification heading="macOS and Linux only" heading-tag="h3" state="info">
  The CLI creates the symlink automatically on macOS and Linux. On Windows, follow the manual step below.
</Notification>

## Choosing a Location

By default the link is created under `.claude/skills/` in the current working directory. Two optional arguments change
where it goes:

```bash
npx --package=@porsche-design-system/components-react pds-skill [dir] [--root]
```

- **`dir`** — the destination parent directory for the link. Defaults to `.claude/skills`. Pass any other directory to
  place the link elsewhere, e.g. `pds-skill .agents` or `pds-skill .github/skills`. The link name (the package name) is
  always appended, and absolute paths are honored as-is.
- **`--root`** — resolve a relative `dir` against the **project root** (the nearest ancestor containing a `.git` entry)
  instead of the current directory. Useful in a monorepo where you run the command inside a subpackage but want the link
  at the repo root. With an absolute `dir`, `--root` has no effect. If no `.git` ancestor is found, the command fails
  rather than guessing.

Note that Claude Code only auto-discovers skills under `.claude/skills/`; use a different directory only when another
tool consumes it from there.

## How It Works

Claude Code only auto-discovers skills under `.claude/skills/` (project) or `~/.claude/skills/` (personal). A skill
sitting in `node_modules` is not discoverable on its own — hence the symlink.

Because the symlink points into the installed package, the content the skill exposes always equals the **installed
version's** content. There is no separate sync step and no possibility of a docs/version mismatch: bumping the installed
package version updates the exposed content automatically.

Direct referencing into `node_modules` works on **npm**, **Yarn Classic (v1)**, **pnpm** (via its transparent symlink
layout) and **Bun**.

## Windows

The CLI does not create symlinks on Windows automatically. Create the link manually from your project root with
`mklink /D` (directory symlink):

```bat
mklink /D ".claude\skills\porsche-design-system-components-react" "node_modules\@porsche-design-system\components-react\skill"
```

Adjust both the package path and the link name (`components-js` / `components-angular` / `components-react` /
`components-vue`) to match your framework.

<Notification heading="Symlink permissions" heading-tag="h3" state="warning">
  Creating symlinks on Windows requires either **Developer Mode** enabled or running the terminal **as administrator**.
</Notification>

## Yarn PnP

Yarn Berry's Plug'n'Play (`nodeLinker: pnp`) is **not supported**: it has no `node_modules` directory for the symlink to
target. If you use Yarn Berry, opt into the classic node-modules linker by setting the following in your `.yarnrc.yml`,
then reinstall:

```yaml
nodeLinker: node-modules
```

## Updating & Reinstalling

The skill content is effectively **read-only**. It lives in `node_modules`, so any edits you make to it are **lost on
the next install**. Do not edit the skill files directly.

The only consumer-side state is the symlink itself. If it ever breaks — for example after reinstalling dependencies, or
after upgrading to a version that newly ships the skill — simply **re-run the CLI** to recreate or repair it:

```bash
npx --package=@porsche-design-system/components-{js|angular|react|vue} pds-skill
```
