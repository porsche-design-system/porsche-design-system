# Claude Code Skill

<TableOfContents
  headings={['Installation', 'Choosing a Location', 'How It Works', 'Windows', 'Yarn PnP', 'Updating & Reinstalling']}
/>

Each Porsche Design System wrapper package ships a [Claude Code](https://docs.claude.com/en/docs/claude-code/overview)
skill named after the package — `porsche-design-system-components-js`, `…-angular`, `…-react` or `…-vue`. The skill
gives your AI assistant **version-exact** knowledge of the Porsche Design System components, styles and tokens that
match the exact package version you have installed, so it can answer questions, generate new code, and review or fix
existing usage.

The skill content lives inside the installed package in `node_modules`. To make it discoverable, a small CLI links the
package skill into the skills directory used by your AI assistant.

## Installation

The wrapper package must already be installed in your project or workspace. Run the bundled CLI from that project or
workspace, passing both the installed wrapper package and the destination skills directory:

```bash
# Vanilla JS
npx --package=@porsche-design-system/components-js pds-skill @porsche-design-system/components-js .claude/skills

# Angular
npx --package=@porsche-design-system/components-angular pds-skill @porsche-design-system/components-angular .claude/skills

# React
npx --package=@porsche-design-system/components-react pds-skill @porsche-design-system/components-react .claude/skills

# Vue
npx --package=@porsche-design-system/components-vue pds-skill @porsche-design-system/components-vue .claude/skills
```

The `--package=…` option tells `npx` which package provides the shared `pds-skill` executable. The first positional
argument tells the CLI which installed wrapper contains the target skill. The CLI resolves that package from the current
project instead of from the executable location, so it cannot accidentally link another installed wrapper or an `npx`
cache copy.

Equivalent commands using other package managers, shown for React:

```bash
# pnpm
pnpm exec pds-skill @porsche-design-system/components-react .claude/skills

# Yarn with nodeLinker: node-modules
yarn pds-skill @porsche-design-system/components-react .claude/skills

# Bun
bunx --no-install pds-skill @porsche-design-system/components-react .claude/skills
```

This creates the symlink `.claude/skills/porsche-design-system-components-<framework>` (e.g.
`.claude/skills/porsche-design-system-components-react`) pointing at the selected package's `skill/` directory. Because
the link name comes from that skill's `SKILL.md`, installing more than one wrapper links each skill side by side.

The command is **idempotent**: re-running it repoints or repairs the symlink it owns (including a dangling link from a
previously removed package), while an already-correct link is left unchanged. If the package is not installed locally or
does not ship a skill, the CLI fails with guidance instead of linking cached or unrelated content.

  The CLI creates a directory symlink on macOS and Linux and a directory junction on Windows.
</Notification>

## Choosing a Location

The package and destination directory are required; `--root` is optional:

```bash
npx --package=@porsche-design-system/components-react pds-skill <package> <dir> [--root]
```

- **`package`** — one locally installed `@porsche-design-system/components-{js|angular|react|vue}` wrapper.
- **`dir`** — the destination parent directory for the link, e.g. `.claude/skills`, `.agents` or `.github/skills`. The
  skill name is always appended, and absolute paths are honored as-is.
- **`--root`** — resolve a relative `dir` against the **project root** (the nearest ancestor containing a `.git` entry)
  instead of the current directory. Useful in a monorepo where you run the command inside a subpackage but want the link
  at the repo root. With an absolute `dir`, `--root` has no effect. If no `.git` ancestor is found, the command fails
  rather than guessing.

Note that Claude Code only auto-discovers skills under `.claude/skills/`; use a different directory only when another
tool consumes it from there.

## How It Works

Claude Code only auto-discovers skills under `.claude/skills/` (project) or `~/.claude/skills/` (personal). A skill
sitting in `node_modules` is not discoverable on its own — hence the symlink.

Because the link points into the locally resolved package, the content it exposes equals the **installed version's**
content. Re-run the CLI after reinstalling or upgrading dependencies so it can repoint the link if the package manager
changed the physical package location.

Local package resolution works with **npm**, **Yarn using the node-modules linker**, **pnpm** and **Bun**.

## Windows

On Windows, the CLI creates a directory junction automatically, without requiring Developer Mode or administrator
permissions. If junction creation fails because of destination permissions or filesystem restrictions, create it
manually from your project root:

```bat
mklink /J ".claude\skills\porsche-design-system-components-react" "node_modules\@porsche-design-system\components-react\skill"
```

Adjust both the package path and the link name (`components-js` / `components-angular` / `components-react` /
`components-vue`) to match your framework.

## Yarn PnP

Yarn Berry's Plug'n'Play (`nodeLinker: pnp`) is **not supported** because an operating-system link cannot target Yarn's
virtual ZIP filesystem; the CLI reports this explicitly. Opt into the node-modules linker, then reinstall:

```yaml
nodeLinker: node-modules
```

## Updating & Reinstalling

The skill content is effectively **read-only**. It lives in `node_modules`, so any edits you make to it are **lost on
the next install**. Do not edit the skill files directly.

The only consumer-side state is the symlink itself. If it ever breaks — for example after reinstalling dependencies, or
after upgrading to a version that newly ships the skill — simply **re-run the CLI** to recreate or repair it:

```bash
npx --package=@porsche-design-system/components-react pds-skill @porsche-design-system/components-react .claude/skills
```
