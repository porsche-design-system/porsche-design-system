## Accessibility support

### Keyboard

| Key / state               | Function                                                                                          |
| ------------------------- | ------------------------------------------------------------------------------------------------- |
| `Tab`, `Shift-Tab`        | Moves focus to the next (or previous) focusable element.                                          |
| `0`–`9`                   | Enters a digit in the focused input, replacing any existing digit, then moves focus to the next input. |
| `Backspace`               | Clears the focused input. If it is already empty, clears the previous input and moves focus there. |
| `Delete`                  | Clears the focused input. If it is already empty, clears the next input and moves focus there.    |
| `ArrowLeft`, `ArrowRight` | Moves focus to the previous or next input. Does not wrap.                                         |
| `Home`, `End`             | Moves focus to the first or last input.                                                           |
| `Enter`                   | Submits the surrounding form when native submit rules allow it.                                   |

### ARIA enhancements

#### Internal **ARIA** that is managed by the component:

| ARIA                            | Usage                                                                                 |
| ------------------------------- | ------------------------------------------------------------------------------------- |
| `aria-label="STRING"`           | Names each input by its position in the group, for example `1 of 4`.                  |
| `aria-describedby="IDREF"`      | References the status message when `state` and `message` are set.                     |
| `role="status"`, `role="alert"` | When `message` and `state` or `loading` prop change, the status message is announced. |

## Development considerations

### Disabled state

In general, avoid using the `disabled="true"` state. Disabled elements are no longer focusable and may be missed by
screen reader users. They can also confuse sighted users if the reason they are disabled is not made clear.

### Common do's and don'ts

- **Do** provide a clear `label` that describes what the code is for.
- **Do** use `description` to explain where users can find the code.
- **Do** use the component state/message API so validation and status changes are announced.
- **Don't** use `hide-label` without an accessible name.
